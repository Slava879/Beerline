Прототип системы автоматического планирования маршрутов сервисных инженеров.
Принимает заявки (CSV / ручной ввод), геокодирует адреса, раскладывает по мастерам с учётом навыков, оборудования, окон клиентов и смен мастеров, строит карты маршрутов.

## 2. Схема решения
### 2.1. Интерфейс
Диспетчерская страница (DispatcherPage.jsx) — единый экран:

слева — панель заявок и мастеров;

справа — iframe с HTML-картой маршрутов (Leaflet);

три вкладки заявок: Не распределённые, Распределённые, Отменённые клиентом;

у каждой карточки — кнопка i с обоснованием решения алгоритма (в дальнейшей версии будет расписано достаточно подробно с максимально необходимым обоснованием);

у распределённой — этапы работы (Выехал → Начал → Завершил), кнопка смены мастера, отмена клиентом;

### 2.2. Алгоритм
Ядро — backend/app/services/algorithm.py:

Жадная вставка с regret-эвристикой (regret_insert) — для каждой заявки рассматриваются все мастера и все позиции в их маршрутах; выбирается вариант с минимальной стоимостью, но с приоритетом для заявок, у которых «второй лучший» вариант сильно хуже первого.

Локальный поиск (local_search) — 2-opt, relocate, or-opt (сегменты 2 и 3), обмены задач между маршрутами.

Минимизация мастеров (minimize_engineers) — пытается освободить часть мастеров, переложив их задачи на других.

ALNS (alns) — последовательные итерации destroy/repair c адаптивными весами операторов и «мягким» принятием ухудшений (имитация отжига).

## 3. Логика оптимизации
### 3.1. Что оптимизируется
Стоимость маршрута мастера:
```
text
cost = total_km                  # пробег
     + WAIT_COST_PER_MIN × wait  # штраф за ожидание
     + penalty                   # штрафы (см. ниже)
     + NEW_ENGINEER_PENALTY      # если мастер раньше не использовался
Все константы — в начале algorithm.py.
```

### 3.2. Штрафы
|Штраф| 	Когда срабатывает	|Значение по умолчанию|
|---|---|---|
LATE_PENALTY_PER_MIN |	работа закончилась позже окна клиента |	60 мин
OVERTIME_PENALTY_PER_MIN|	работа закончилась позже конца смены|	15 мин
LONG_TRAVEL_PENALTY_PER_MIN	|между двумя точками > MAX_TRAVEL_MIN	|300 × (t/20)³
URGENT_EARLINESS_PENALTY_PER_MIN|	срочная заявка начата позже urgent_ref_time|	50 мин
EQUIPMENT_MISMATCH_PENALTY	|пешеход/велосипедист везёт оборудование	|300
NEW_ENGINEER_PENALTY	|мастер первый раз получает заявку в решении|	3000


### 3.3. Обязательные метрики
Метрики, которые всегда считаются по итогу распределения:

assigned / total — сколько заявок из пула назначено;

unassigned — список с причинами;

total_km — суммарный пробег всех маршрутов;

total_wait — суммарное ожидание мастерами клиентов;

end_day — время возврата мастера в офис.

Хранятся в возвращаемом значении distribute_orders и выводятся в лог бэка.

### 3.4. Учитываемые ограничения
Жёсткие (нельзя нарушать, иначе решение невалидно):

нельзя начать заявку раньше смены мастера;

мастер обязан успеть приехать в окно заявки (прибытие ≤ window_end);

работа + возврат в офис не должны выходить за конец смены;

у мастера есть нужный навык для типа заявки;

у мастера хватает оборудования на все свои заявки;

для пешехода/велосипедиста — лимит оборудования LIGHT_TRANSPORT_MAX_EQUIPMENT = 3 шт.

Мягкие (за нарушение — штраф, не запрет):

работа может закончиться после окна клиента (просрочка);

возможна переработка смены (если SHIFT_OVERTIME_TOLERANCE_MIN > 0);

длинная дорога между двумя точками.

### 3.5. Специальный приоритет
Срочные заявки (priority = 0, тип «Глобальная проблема») получают priority = -1 в алгоритме — они всегда рассматриваются первыми, а при вставке в маршрут запускается дополнительная локальная оптимизация _reorder_for_urgent, чтобы срочная оказалась как можно раньше.

## 4. Тестовый набор данных
### 4.1. Формат CSV
Колонки распознаются по синонимам (см. HEADER_SYNONYMS в districts.py):

task_id	«заявка», «id», «№», «номер заявки»	да	4–6 цифр

bk	«тип заявки BK», «BK», «тип заявки бк»	нет	см. справочник ниже

hd	«тип заявки HD», «HD»	нет	строка

start	«начало», «время с», «окно с»	да	DD.MM.YYYY HH:MM

end	«окончание», «время по», «окно по»	да	DD.MM.YYYY HH:MM

date	«дата», «дата визита», «плановая дата»	нет	DD.MM.YYYY

district	«район», «округ»	нет	строка

address	«адрес», «адрес объекта»	да	строка

gigabit	«гигабитное подключение»	нет	строка

Разделитель — ;, , или \t (определяется автоматически).

Кодировка — UTF-8 (BOM допускается).


### 4.2. Единицы измерения
|Величина|	Единица|
|---|---|
координаты	|градусы (lat, lon), WGS-84
расстояния|	километры
время	|минуты / HH:MM
скорости	|км/ч (пешеход 10, велосипед 10, автомобиль 20)
окна клиентов	|time в orders.window_start / window_end|

### 4.4. Геокодирование
LocationIQ (geocoding.py) — адрес → координаты.

Принимается попадание со score ≥ 6.0. Если ничего не нашлось — заявка уходит в «Не распределённые» с причиной «не удалось геокодировать».

Диспетчер может задать координаты вручную (кнопка «📍 Задать координаты»).

### 4.5. Расчёт расстояний
Haversine × KOEF_ROAD = 1.4 (поправка на реальные дороги);

кэш _travel_cache — чтобы не пересчитывать одинаковые пары;

для карт — реальные маршруты через Mapbox Directions API.


## 5. Известные ограничения прототипа
Статичная геометрия. Геометрия маршрута берётся один раз при распределении и
перерисовывается только при rebuild_maps.

Часовой пояс. Время пишется через datetime.now() — это локальное время сервера. При доработке можно добавить окно, где будет выбираться диспетчерем часовой пояс

Дедупликация по external_id. При повторной загрузке CSV заявки с уже
существующими external_id игнорируются. Если в CSV изменились поля существующей заявки — изменения не подтянутся. (для доработки: запрасить у диспетчера обновлять поля или не обновлять если они уже есть в БД)

Реальная дорожная обстановка. Расстояния считаются Haversine × 1.4, а не по
реальным дорогам, кроме отрисовки карт (Mapbox используется только для геометрии). Почему рассчитывается так? При бесплатных сервисах рассчитать сотни комбинаций займет значительное время, простая формула, которая справляется не хуже занимает доли секунды для того же действия

Мастеров не больше ~20 на район. regret_insert + local_search на большем
числе мастеров может быть медленным. Из-за особенностей алгоритма, при превышении инженеров 20 на район, время на перебор комбинаций увеличивается в разы (на доработку: найти способы оптимизировать и при большом количестве мастеров)

Смена мастера посреди дня. Если мастер снят со смены, его задачи уходят в пул, но перепланирование делается вручную — кнопкой «Распределить заявки». Так же при назначении срочной заявки, распределение тоже необходимо запустить вручную. (на доработку: проработать автоматизацию перераспределения)

Ошибки геокодинга. Порог MIN_ACCEPT_SCORE = 6.0 иногда пропускает неудачные
попадания (например, «Москва, Тверская» на «Москва, Тверская, 1»). Диспетчеру
приходится править координаты вручную. (на доработку: изучить и рассмотреть более надежные способа парсера адреса и доработать его, также есть ограничения на бесплатные версии, что некоторые адрема туда не подгрудены, а некторые могут считаться некорректными)

## 6. Идеи развития
### 6.1. Оптимизация алгоритма
Оптимизация под реальные дороги. Заменить Haversine на OSRM/Valhalla с кэшем
матрицы расстояний между всеми парами за день.

Многоагентный ALNS. Сейчас ALNS работает по одному решению; можно добавить
параллельные цепочки с разными seed'ами и выбирать лучшее.

Учёт риска пробок. OSRM / Яндекс.Пробки дают ETA по времени суток, а не
статичные 20 км/ч.

Внешнее перераспределение при опоздании. Если now > planned.in_progress,
автоматически пересобирать оставшиеся заявки.

### 6.2. UI
Drag&drop заявок из списка в маршрут мастера.

Планировщик-календарь в стиле Google Calendar для визуализации загруженности.

Мобильный экран мастера — кнопки Выехал / Начал / Завершил c фиксацией в системе.

### 6.3. Данные и интеграции
Реальные источники заявок. Интеграция с CRM / BPM через webhook.

Двусторонний sync с мобильным приложением мастера (адаптив под телефон). Статусы меняются в приложении → WebSocket → диспетчер видит изменения в реальном времени.

Справочник адресов. Локальный индекс адресов района (типа «DaData» или
собственный Postgres + pg_trgm) — геокодинг быстрее и точнее.


### 6.4. Инфраструктура
Планировщик. Cron / Celery-задача, которая раз в 10 минут прогоняет
auto_update_statuses и рассылает WS-события.

Логи действий. Audit-таблица order_history — кто, когда и что менял.

Метрики. Prometheus + Grafana: сколько заявок назначено, средний пробег,
средняя задержка, доля отменённых.

Мультитенантность. Разделение по компаниям/участкам с изоляцией данных.

### 6.5. Ограничения, которые стоит снять в первую очередь
Часовой пояс — дать возможность выбора диспетчеру во всех datetime.now().

Реальные дороги — перевести расчёт ETA на OSRM.

Смена мастера в середине дня — авто-перераспределение вместо ручного.

Дедупликация CSV — добавить режим upsert, если нужно обновлять существующие.
